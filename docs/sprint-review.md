# Project Summary

Briefly describe your solution.

What did you build?

I built a weather forecast application that allows users to search for cities around the world and view current weather conditions as well as hourly and daily forecasts.The application includes:

- City search functionality.
- Current weather information.
- Hourly and daily forecasts.
- Favorite cities management.
- Temperature unit conversion between Celsius and Fahrenheit.
- Loading and error handling states.

The goal was to create a clean, responsive and maintainable application while keeping the code organized and scalable.

# Project Architecture

Describe how you organized the project. Why did you choose this structure?

I organized the project using a Feature-Based Architecture. Instead of grouping files by technical responsibility (components, hooks, services, etc.), I grouped them by business domain:

- search_by_city
- weather_forecast
- favorites_cities

Each feature owns its own components, hooks, services and state when appropriate. I chose this structure because it scales better as the application grows. Features remain isolated, easier to maintain and easier to understand for new developers joining the project. Shared functionality was placed in common, utility and infrastructure folders to avoid duplication while keeping domain logic inside the corresponding feature.

# Technical Decisions

## State Management

I used two different approaches depending on the type of state:

- React Query for server state.
- Context API for global UI state.

React Query manages API requests, caching, loading states and error handling.

## Context API manages:

- Favorite cities.
- Temperature unit preferences.

This keeps server state and client state clearly separated.

## Styling Solution

I used Tailwind CSS because it allows rapid UI development and keeps styling consistent across the application.

## Data Fetching

I used React Query combined with Axios. This simplified data fetching and provided:

- Request caching.
- Automatic refetching.
- Loading states.
- Error handling.

## Routing

I used React Router to manage navigation between pages and features.

## Component Architecture

Components were divided into:

- Reusable shared components.
- Feature-specific components.

Business logic was extracted into custom hooks whenever possible to keep UI components focused on presentation.

# Challenges

What was the most difficult part of the challenge?

How did you solve it?

The most challenging part was coordinating the city search flow with weather retrieval. The application first needs to obtain city coordinates through a geocoding request and then use those coordinates to retrieve weather data. To solve this, I separated responsibilities into dedicated hooks and used React Query to manage asynchronous requests and state transitions. This made the data flow more predictable and easier to maintain.

# Trade-offs

If you had to simplify or postpone something, what was it?

Why did you make that decision?

Given the time constraints, I focused on delivering a clean architecture and core functionality rather than implementing every possible enhancement.

For example:

These decisions allowed me to prioritize the most important user-facing features and overall code quality.

# Self Assessment

Looking back at your implementation...

### What part are you most proud of?

I am most proud of the forecast pagination feature.

The weather API returns a large amount of forecast information, and displaying all of it at once would make the interface difficult to navigate. I designed and implemented a custom pagination system that allows users to browse forecast data in smaller, more manageable sections. Currently it works with 4 items per page and a total of 16 elements, but this can be changed for more items.

This required coordinating state management, data slicing and UI updates while keeping the components reusable and easy to maintain. I also separated the pagination logic from the presentation layer to keep the code clean and aligned with the overall architecture of the project.

I am particularly satisfied with this feature because it improved both the user experience and the maintainability of the codebase.

### What part would you refactor?

I would refactor the favorite cities feature.

Currently, the favorites functionality is implemented using a Context API and mock data, which works well for the scope of this challenge. However, if the application continued to grow, I would improve this area by introducing persistence through a backend service.

I would also review some of the shared utility and mapping logic to move feature-specific code closer to the modules that use it. This would improve encapsulation and make each feature even more self-contained.

### If you had to start again, what would you do differently?

I would introduce testing earlier in the development process and define some domain models and interfaces upfront. This would make refactoring easier and provide greater confidence when adding new features.
